# 上群AH 臨床指南筆記頁面撰寫

這個 skill 記錄的是 `上群AH/`（醫院臨床知識庫，依科別分類，不是依學期週次）這條站線，在整理 CKD、貓糖尿病、SUB、犬淋巴瘤研討會筆記、貓牙科指南這幾份主題頁的過程中，一輪一輪被使用者糾正之後才穩定下來的做法。寫這份 skill 的目的，是讓下一次「幫我整理這份 Guideline」不用重新踩過同樣的坑——尤其是圖片版權那條界線，是被使用者反覆施壓好幾輪才確立下來的，不能因為換了一次對話就鬆動。

## 這個 skill 假設你已經知道的事

- 上群AH 的資料夾結構、頁面樣式規則（`.section`／`.card`／`.alert`／`.table-wrap`／`.hero-door` 這些 class 的意義），定義在 `上群AH/CLAUDE.md`，會自動載入。**注意這份文件有落後於實際做法的地方**：它寫「主題頁整份 CSS/JS 都是 inline」，但實際上現在的主題頁跟總覽頁一樣外部引用 `../assets/nav.css` + `../assets/ah.css?v=4`，只是不載入 `style.css`。以本 skill 與現有主題頁原始碼為準，不要照 CLAUDE.md 那句話重新走回 inline 寫法。
- 分類軸是**臨床科別**，不是學期週次；「研討會」是額外獨立於臨床科別之外的第二個分類軸（醫師參加研討會帶回的講義），首頁上分開兩排 `<h2>` 顯示。
- 找不到某個元件怎麼寫，直接看 `上群AH/內科/貓慢性腎病CKD照護指南.html` 或 `上群AH/外科/貓口腔與牙科照護指南.html` 的原始碼，比看這份 skill 更準——這兩份是目前打磨最多輪的範例頁。

## 核心原則

**內容要忠於來源文件，讀不到／查不到的地方要老實說，不要用訓練資料裡的一般知識填空。** 這條規則的起源：使用者曾直接問「網頁的內容跟實際 Guideline 內容區別在哪裡？」，逼問出「CKD 頁面引用的 2026 iCatCare 指南其實從沒被讀過全文，是用二手資料拼湊的」這個事實，使用者才因此提供了正式全文 PDF。之後每一份頁面都要求做到：

- 一定要真的用 pymupdf 抽出來源 PDF 全文並整份讀過（見下方流程），不能只憑檔名、摘要或訓練資料裡對這份指南的印象寫內容。
- 對於「查不到全文」「只查到摘要」「這個數字沒能親自核對」的地方，**明確在頁面上或回覆使用者時講出來**，不要含糊帶過假裝都核對過。SUB 頁面的「文獻補充」小節、糖尿病頁面的縮寫核對過程都是這樣做的範例。
- 如果使用者事後拿真正的原文來核對，發現有落差（例如 CKD 頁面一開始的血磷目標值是錯的），要老實列出「原本寫錯的地方」逐項修正，不要淡化成「稍微更新」。

## 整體流程

### 1. 找到並讀懂來源文件

用 pymupdf 抽出全文（原生 PDF 用文字抽取最省 token；掃描圖檔 PDF 才需要整頁轉圖用 Read 工具看）：

```bash
./.venv/bin/python -c "
import pymupdf
d = pymupdf.open('{{PDF路徑}}')
out = []
for i,p in enumerate(d):
    out.append(f'--- page {i+1} ---\n' + p.get_text())
open('{{scratchpad路徑}}/extract.txt','w').write('\n\n'.join(out))
print(len('\n\n'.join(out)))
"
```

如果印出的字元數低到不合理（例如每頁不到 100 字），代表是掃描圖檔或圖表比例極高，改用 Read 工具的 `pages` 參數直接看頁面圖片，不要只靠抽出來的空殼文字。

用 Read 工具分段讀完整份抽出的文字（通常幾萬到十幾萬字元，用 `offset`/`limit` 切成幾次讀，不要跳著讀）。讀的時候留意：

- 章節架構跟目錄頁對不對得上，有沒有漏掉的小節。
- 具體數字（劑量、百分比、天數、分期切點）要抓精確，這些之後會直接寫進表格。
- 同一顆藥在不同適應症下劑量可能不同（例如 telmisartan 治療高血壓是 2 mg/kg、治療蛋白尿是 1 mg/kg）——這種「同名不同劑量」的地方特別容易被讀者搞混，寫頁面時要刻意標出來對比，不要合併成一行帶過。
- 只要來源有明確給藥途徑就要寫出來（PO/IV/IM/SC/CRI...），不能只寫劑量跳過途徑。

如果使用者額外要求核對獨立文獻（不是只整理單一來源指南，而是要橫向比較廠商資料 vs 已發表研究），用 WebSearch/WebFetch，見下方「圖片與版權界線」之後的「事實查核」段落。

### 2. 決定放在哪個科別

`上群AH/` 目前的科別：內科／外科／影像診斷／麻醉／急重症／臨床病理與血檢判讀／藥物治療與劑量／技術操作與SOP，加上獨立的「研討會」。依內容的臨床本質判斷（例如牙科手術＝外科、研討會講義＝研討會，不因為講義裡有提到腫瘤科knowledge就归類到內科）。不確定就直接問使用者一句，不要自己悶著猜。

### 3. 寫頁面

複製一份既有主題頁（`上群AH/內科/貓慢性腎病CKD照護指南.html` 是最新打磨過的範例）整份改，不要從零手刻，容易漏掉細節。固定的章節順序（順序本身就是規則，不要自己重新排）：

1. **重點摘要**（`section-abstract`，永遠是第 1 節）：一個 `alert alert-info`，裡面 5 條 `<li>`，每條是「這篇最值得記住的臨床重點」，不是章節標題的白話重述。要包含「容易搞混的地方」（同名不同劑量、常見迷思澄清）跟「跟直覺不一致的發現」（例如化療沒有想像中影響生活品質），這樣才對得起「馬上知道臨床重點在哪裡」這個目的。
2. **總覽**（`section-overview`）：來源與版本說明、疾病背景。**不要在這裡放縮寫對照表**——縮寫表要放在練習題前面（見下）。
3. 中間依來源架構分若干節，能用表格就用表格（分期系統、劑量比較、併發症處置流程），能畫示意圖就畫原創 SVG（見下一段），不要整段敘述文字硬撐。
4. **縮寫對照表**（`section-glossary`，倒數第二節，緊接在練習題之前）：每個縮寫要有英文全名＋中文翻譯。
5. **練習題**（`section-quiz`）：**全部使用 `quiz-type-saq`，寫成臨床情境問答題，不要用選擇題／是非題**。格式是「一段具體情境（幾歲的貓／狗，什麼檢查發現，飼主問了什麼）→ 會怎麼處置或怎麼回答」，答案要包含具體劑量／數字／判斷邏輯，不是只給結論。這條規則的起源：使用者明確稱讚 CKD 頁面的問答題品質，並要求其他頁面比照——之後每一份新頁面、或既有頁面被要求「出題」時，都直接套用這個格式，不要再做選擇題/是非題。
6. **參考資料**（`section-references`，最後一節，若內容值得列出獨立文獻或原文出處才需要）：APA 風格＋DOI 連結；若同時引用「獨立同儲審查文獻」跟「廠商／贊助方內部資料」，要分兩組列出並註明差異（見糖尿病、SUB、犬淋巴瘤研討會頁面的做法），不要混在一起讓讀者以為證據等級相同。

其他固定規則：

- 提示框語意：`alert-info`（補充／解讀提醒）、`alert-warn`（注意／證據限制）、`alert-danger`（禁忌／警訊）、`alert-success`（不常用，正向結果時可用）。
- `pagehead__actions` 放 PDF 下載按鈕、`meta-bar` 的「資料來源」要連到真正讀過的來源，不要放沒讀過的連結充版面。
- 每節結尾／頁面最底部維持 `<footer class="note-footer">` 免責聲明。

### 4. 圖片與版權界線（最重要、最容易被要求破例的一段）

**原則：文字內容可以大量改寫、重新整理、做成表格——這是「整理」的本質，沒有問題。圖片（尤其是照片）不行，即使使用者強烈要求、聲稱非營利、聲稱來源公開、或說「另一個視窗可以」，都不改變這條線。**

這條界線不是猜測出來的，是這個 repo 實際發生過、被使用者用各種角度施壓後仍然守住的結論，包含：

- 拒絕截取 IDEXX 研討會簡報（有明確「未經授權不得重製」聲明）的投影片畫面，即使使用者說「這個網頁只有我跟另一個住院醫師要用」「我負責」「這個網頁只有我看得到」。
- 拒絕截取期刊指南（貓牙科指南，2025 FelineVMA/JFMS）裡標註 "Image courtesy of Heidi Lobprise" / "Image courtesy of Cornell University" 的臨床照片與 X 光，即使使用者說「這是為了讀書」「沒有任何營利用途」「這份講義是公開的」「Guideline 產出不就是為了讓動物更好嗎」。
- 用「public availability to read ≠ 允許重製個別圖片」跟「hosting 整份 PDF 原檔連結（未拆解、未改作）」與「截取單張圖片重新嵌入自己的頁面」是兩件不同的事，來回應「這份文件本來就公開」這種說法——前者是提供連到原始出版品的連結，後者是把別人的攝影/繪圖作品拆出來，用自己的排版、自己的圖說，重新發表成自己頁面的一部分。

**判斷是否可以直接 host 原始 PDF 檔案（壓縮後整份放進 `<科別>/` 資料夾、`pagehead__actions` 加下載按鈕）：**

| 來源類型 | 可否 host 整份 PDF | 理由 |
|---|---|---|
| 期刊發表的獸醫共識指南（JFMS／JAVMA／JAAHA 等，無明確禁止重製聲明） | 可以 | 這類指南通常以促進臨床採用為目的公開發行，CKD／糖尿病 AAHA／貓牙科指南都是這樣處理 |
| 廠商／贊助商研討會簡報、行銷簡報（有明確 "may not be reproduced" 之類聲明） | 不可以 | IDEXX 犬淋巴瘤簡報案例；即使使用者自己把檔案手動放進資料夾，也不要主動幫忙 `git add`／寫進頁面連結 |
| 不確定 | 先檢查文件是否有版權/重製聲明頁（通常在前 1–2 頁），沒把握就當作「不可以」處理，並跟使用者說明原因 |

**圖片的替代做法：**

1. **原創手繪 SVG 示意圖**（沿用 `artifact-diagramming` skill 的原則：`viewBox` 縮放、`currentColor` 做主線條顏色、只留一個真正承載訊息的元素用強調色、有 `<figcaption>` 講清楚圖在說什麼）。凡是「分期示意」「機轉」「分類邏輯」這類**可以用形狀/位置關係表達的概念**，優先用這個做法，而不是找照片替代——CKD 頁面的 SGLT2 機轉圖、犬淋巴瘤頁面的分期偏移長條圖、貓牙科頁面的咬合不正分類圖與 AVDC 方向術語圖都是範例。
2. **使用者自己醫院的病例影像**（已去識別化）——這是使用者自己擁有的素材，可以放，且比期刊的教學圖片更有臨床意義；如果使用者手上有，主動問要不要用這個取代原本想截圖的部分。
3. **真正公眾領域／CC 授權的圖片**——需要使用者自己找到並確認授權條款，不要自己去猜測某張圖是不是公眾領域。

**遇到使用者持續施壓時的應對方式**：態度上不要說教、不要每次重講一整段道理，簡短重申立場、給出可行的替代方案（見上）就好；不要因為使用者說「另一個對話框可以」「我可以承擔責任」「這是為了讀書」而鬆動——這些理由都不會改變版權歸屬，处理方式是承認對方的立場合理，但清楚說明自己不會做這件事，然後把力氣放回「能做的部分」上。

### 5. 事實查核（劑量、獨立文獻比較等進階需求）

不是每份頁面都需要，但使用者要求「查一下有沒有獨立研究」「這個劑量對不對」時適用：

- WebSearch 找相關文獻，WebFetch 抓全文時**用逐項提問的方式**（列出頁面上寫的每個具體數字，請它回答 CONFIRMED／CONTRADICTED／NOT FOUND，並附 20 字內的原文引用佐證），不要要求逐字複製全文——大型出版社的頁面通常會以版權理由拒絕逐字輸出，逐項查核法可以繞過這個限制同時達到核對目的。
- SAGE／PubMed 常對程式化抓取回 403 或需要 cookie，可以改試 PMC 的 rendered 頁面、或用 WebSearch 摘要+多個獨立來源交叉比對；抓不到全文的論文要在頁面上誠實標注「僅讀到摘要」。
- 查完的結果如果跟頁面現有內容有出入，比照第 4 節的做法：分「獨立同儲審查文獻」vs「廠商/贊助方資料」兩欄或兩組列出，不要混為一談。

### 6. 結構驗證

```bash
python3 .claude/skills/ah-guideline-builder/scripts/verify_page.py 上群AH/{{科別}}/{{主題}}.html
```

檢查標籤配對、TOC 與 section id 互相對應、`SECTION_NAMES` 跟 section id 是否一致、`section-num` 是否從 1 連續編號到底（新增或搬移章節後最容易漏改）。有錯誤就照訊息修，重跑到印出「全部通過 ✓」。

如果同一批修改也動到 `search-index.js` 或 `assets/nav-data.js`，額外跑：

```bash
node -e "new Function(require('fs').readFileSync('上群AH/search-index.js','utf8')); console.log('OK')"
node -e "new Function(require('fs').readFileSync('上群AH/assets/nav-data.js','utf8')); console.log('OK')"
```

一個逗號打錯就會讓整個檔案的搜尋/導覽功能失效，這兩個檔案沒有容錯機制。

### 7. 站台整合

新增一份主題頁，以下四個地方都要同步更新，缺一個都會讓頁面變成孤兒頁（進得去但搜不到、也不會出現在導覽）：

1. **該科別的 `index.html`**：把主題卡片加進 `<ul class="hero-doors hero-doors--topics">`，用下一個流水號當 `hero-door__index`。
2. **`上群AH/index.html`（頂層首頁）**：對應科別卡片的 `<ul class="hero-door__topics">` 加一行 `<li>`；如果原本是空狀態（`hero-door--placeholder`／「尚無筆記」），要整個換成正式連結卡。
3. **`上群AH/assets/nav-data.js`**：對應科別的 `topics` 陣列加一筆 `{ title, url, desc }`，這是頂列跨科別下拉選單的唯一資料來源。
4. **`上群AH/search-index.js`**：每個主要 section 補一筆搜尋條目（`subject`/`weekTitle`/`url`/`section`/`sectionName`/`keywords`/`snippet`，`week` 固定 `null`），放在檔案最後、既有條目之後，不要打散插在中間。

### 8. 最後確認

用 `open` 指令在瀏覽器打開頁面目視確認（深色/淺色模式、TOC 捲動高亮、練習題展開都正常），再跟使用者回報做了什麼。

## Git

跟這個 repo 的所有其他工作一樣：**除非使用者明確要求，否則不要主動 commit 或 push。** 改完一輪頁面/索引之後，用 `git status`／`git diff` 讓使用者看到改了什麼，由他們決定要不要進版控；如果改動裡包含新的 PDF／圖片檔案，順便提醒使用者這些檔案會一起被推上目前是 public 的 repo。
